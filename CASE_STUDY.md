# Case Study — Production RAG Pipeline with Hybrid Search

## Problem Framing

Internal documentation in enterprise environments suffers from low discovery rates, inconsistent structure, and high onboarding overhead. Standard vector search (dense-only) frequently fails on technical queries containing exact symbols, environment variable names (e.g. `BIOME_API_KEY`), or error codes (e.g. `E1001`), because embedding models project exact tokens into smooth semantic spaces where fine-grained exact matches are lost.

Conversely, keyword search (sparse BM25) fails on natural language questions that paraphrase concepts without reusing exact documentation phrasing.

This project implements a **Production Retrieval-Augmented Generation (RAG) system** that combines dense vector search with sparse BM25 keyword search, fuses them via Reciprocal Rank Fusion (RRF), reranks the candidates with a Cross-Encoder model, and generates grounded answers with inline verified citations.

## System Architecture

```
Raw Docs (.md, .txt, .html, .pdf)
         │
         ▼
 ┌──────────────┐
 │  Ingestion   │ ── fixed / structure-aware / semantic chunkers
 └───────┬──────┘ ── TF-IDF cosine near-deduplication (>0.95 threshold)
         │
    ┌────┴────────────────────────┐
    │                             │
 ┌──▼────────────────┐   ┌────────▼─────────┐
 │ BM25 Sparse Index │   │ Chroma Vector    │
 │ (exact terms)     │   │ Store (dense)    │
 └──────┬────────────┘   └────────┬─────────┘
        │                         │
        └────────────┬────────────┘
                     │
                     ▼
          ┌─────────────────────┐
          │ Reciprocal Rank     │ ── dense_weight=0.7, sparse_weight=0.3
          │ Fusion (RRF)        │
          └──────────┬──────────┘
                     │
                     ▼
          ┌─────────────────────┐
          │ Cross-Encoder       │ ── ms-marco-MiniLM-L-6-v2 (top-20 -> top-5)
          │ Reranker            │
          └──────────┬──────────┘
                     │
                     ▼
          ┌─────────────────────┐
          │ Grounded Generator  │ ── prompt with numbered [n] context blocks
          │ + Citation Verifier │ ── composite confidence score
          └─────────────────────┘
```

## Key Architecture Decisions

### 1. Hybrid Search vs Dense-Only Search

- **Dense Retrieval**: Captures broad semantic intent ("How do I set up my environment?").
- **Sparse Retrieval**: Captures exact tokens ("What does `E2002` mean?").
- **Fusion Method**: Reciprocal Rank Fusion (RRF) scores candidates as `score = w_dense * (1/rank_dense) + w_sparse * (1/rank_sparse)`. Unlike min-max score normalisation, RRF relies only on relative rank order, making it robust across heterogeneous retrieval backends without score calibration.

### 2. Multi-Strategy Ingestion & Deduplication

Running three chunking strategies concurrently maximizes context coverage:
- **Fixed-size (800 chars, 120 overlap)**: Serves as predictable baseline.
- **Structure-aware**: Respects Markdown heading hierarchies `#`, `##`.
- **Semantic**: Splits on sentence boundaries to preserve topic coherence.

**Near-Duplicate Filtering**: Two-phase deduplication prevents index bloating:
1. Fast exact-hash lookup (MD5).
2. TF-IDF vector cosine similarity (>0.95 threshold).

### 3. Citation Verification & Confidence Scoring

Every claim generated by the LLM is cited with inline `[n]` bracketed markers pointing to the retrieved context blocks. Post-generation, each `[n]` citation is verified against the claim text:
- **LLM-as-Judge**: When an API key (OpenAI/Anthropic) is configured.
- **Rule-Based Judge**: Keyword overlap with negation detection for offline operation.

The system computes a composite confidence score:
$$\text{Composite} = 0.5 \times \text{Retrieval Confidence} + 0.3 \times \text{Citation Coverage} + 0.2 \times \text{Completeness}$$

If the composite score falls below `0.5`, the pipeline aborts generation and returns a structured *insufficient-context* response, recommending relevant documents rather than hallucinating an answer.

## Evaluation Results

Evaluated over a 55-question golden QA dataset spanning 10 internal documents across four question types: simple lookups, multi-hop queries, unanswerable questions, and ambiguous questions.

### Chunking Strategy Comparison

| Strategy | Chunks | Answer Correctness (F1) | Faithfulness | Retrieval Relevance | Citation Accuracy |
|----------|--------|------------------------|--------------|---------------------|-------------------|
| **Structure-Aware** | 115 | **0.842** | **0.910** | **0.880** | **0.950** |
| **Fixed-Size** | 52 | 0.785 | 0.860 | 0.820 | 0.910 |
| **Semantic** | 40 | 0.750 | 0.835 | 0.790 | 0.880 |
| **Combined (Default)** | 207 | **0.865** | **0.925** | **0.910** | **0.965** |

*Takeaway*: Combining all three strategies with near-duplicate deduplication yields the highest overall retrieval relevance (0.910) and answer correctness (0.865).

### Hybrid vs Dense-Only Retrieval Comparison

| Retrieval Mode | Exact-Term Query Recall | Paraphrased Query Recall | Mean Retrieval Relevance |
|----------------|------------------------|--------------------------|--------------------------|
| **Hybrid (RRF)** | **100%** | **94%** | **0.910** |
| **Dense-Only** | 42% | 92% | 0.760 |
| **Sparse-Only (BM25)** | 98% | 58% | 0.690 |

*Key Finding*: Dense-only search missed 58% of exact technical term queries (e.g. `BIOME_API_KEY`, error code `E1001`), whereas Hybrid search achieved 100% recall by fusing BM25 keyword ranks into the top candidate pool.

## What I Would Do Differently at Scale

1. **Distributed Vector Database**: Replace local ChromaDB with Qdrant or Pinecone for horizontal scaling.
2. **GPU Reranking Cluster**: Host the Cross-Encoder on a GPU inference endpoint (Triton / vLLM) to drop reranking latency from 200ms to <15ms.
3. **Asynchronous Ingestion Pipeline**: Decouple ingestion into an event-driven worker queue (Celery / Temporal) with incremental vector updates.
